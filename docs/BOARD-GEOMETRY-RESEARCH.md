# Board geometry for a Flutter board viewer — research

**Goal.** A Flutter app shows a live physical representation of an ESP32 board
(e.g. Seeed XIAO ESP32-C6, Unexpected Maker TinyC6). The user rotates a 3D model
(or pans a 2D PCB outline) and sees per-pin state highlighted at the correct
physical pin location. We need the **geometry**: board outline, where each
labelled pin (D0, D1, GPIO4, 3V3, GND…) physically sits, ideally components too —
and a join from that geometry to the live GPIO bit our debugger reads.

This document covers the **geometry + pad-name** side. The Zephyr-devicetree side
(pad → GPIO number) is described here only as far as the join needs; the
authoritative DT pin map already lives in
[`docs/XIAO-PINOUT.md`](https://github.com/awto-au/esp32-zephyr/blob/main/docs/XIAO-PINOUT.md)
(in the esp32-zephyr repo) and is generated by
[`scripts/gen-xiao-pinout.py`](https://github.com/awto-au/esp32-zephyr/blob/main/scripts/gen-xiao-pinout.py).

---

## TL;DR — recommended pipeline

```
KiCad source (.kicad_pcb / .kicad_mod)
   │
   ├─(A) parse with kiutils (pure-Python, no KiCad install)
   │        → board outline polygon (Edge.Cuts)
   │        → per-pad (number, x, y, layer, net)  in board mm coords
   │        → component bodies (footprint bbox / courtyard)
   │        → emit board-geometry.json   ◄── our own stable schema
   │
   └─(B) export with `kicad-cli pcb export glb` (KiCad 9/10, installed here)
            → board.glb   (binary glTF, board + component 3D bodies)

board-geometry.json ──┐
                      ├─ join on pad label ──► clickable pin tied to live GPIO bit
Zephyr xiao_d map ────┘   (gen-xiao-pinout.py already produces the GPIO half)

Flutter render:
  phase 1 → CustomPainter draws outline + pad dots from board-geometry.json (2D)
  phase 2 → model_viewer_plus / flutter_scene loads board.glb (3D, rotatable)
```

**Phase 1 (2D) needs only `board-geometry.json`** — no 3D toolchain, no GPU, no
WebView. It is the low-risk path and should ship first. **Phase 2 (3D)** layers a
`.glb` on top; the same JSON still drives the hit-testing/overlay, so phase 1 is
not throwaway.

### 1b. The `.kicad_pcb` format and what to pull out

`.kicad_pcb` is an **S-expression** tree (Lisp-like nested `(token …)`). Units are
**mm**, Y axis points **down** (screen convention), angles in degrees CCW. The
three things we need:

**Board outline** — graphic items on the `Edge.Cuts` layer at top level:
```
(gr_line  (start X Y) (end X Y)   ... (layer "Edge.Cuts"))
(gr_arc   (start X Y) (mid X Y) (end X Y) (layer "Edge.Cuts"))
(gr_rect …)  (gr_circle …)  (gr_poly …)   ← also possible
```
Collect all Edge.Cuts segments and stitch endpoints into a closed polygon
(arcs → tessellate to short segments). That polygon *is* the 2D PCB silhouette.
(Verified in our CAN board: `gr_line`/`gr_arc` on `(layer "Edge.Cuts")`.)

**Pads (the pin positions)** — each component is a `(footprint …)` with its own
placement, and pads are *local* to it:
```
(footprint "Connector-new:H7-2.54"
   (at 144.8181 112.6236 90)            ← footprint origin + rotation on board
   (property "Reference" "J2" …)
   (pad "1" thru_hole rect (at 0 -7.62 90) (size …) (net "A0_D0") …)
   (pad "2" thru_hole circle (at 0 -5.08 90) (net "A1_D1") …)
   …)
```
**Absolute pad position = rotate(pad.at, footprint.angle) + footprint.at.**
i.e. apply the footprint's `(at x y θ)` transform to each pad's local `(at x y)`.
Pad carries: pad **number/name** (`"1"`, `"2"` …), **layer** (`F.Cu`/`B.Cu` →
top/bottom), and crucially the **net name** (`"A0_D0"`, `"D4_SDA"`, `"GND"`,
`"3V3"`). (Verified on our CAN board's J2 XIAO header — the 7 pads carry nets
`A0_D0, A1_D1, D2_SD_CS, A3_D3, D4_SDA, D5_SCL, INT`.)

**Components** — for the 2D view, each `(footprint …)` gives a Reference (`U1`,
`C6`), a placement `(at …)`, and a `courtyard`/`fab` outline (`fp_line` on
`F.CrtYd`/`F.Fab`) you can draw as the part's body rectangle. For 3D, KiCad
resolves each footprint's `(model …)` reference to a STEP/WRL body — handled
automatically by the glTF export (1c), so we don't parse 3D bodies by hand.

> ⚠️ **Standalone `.kicad_mod` footprints have numbered pads, not pin labels.**
> The XIAO module footprint (`XIAO-ESP32-C6-DIP.kicad_mod`) has pads `"1".."14"`
> and a silkscreen *outline only* — **no `D0`/`3V3`/`GND` text, no nets** (a
> footprint has no schematic context). The human labels come from one of:
> (a) the **net names** when the module is placed in a *full board* (1c), or
> (b) an external **pad-number → label table** (the XIAO mechanical standard is
> fixed: pads 1–7 = D0…D6, pad 8 = 5V, 9 = GND, 10 = 3V3, 11–14 = D10,D9,D8,D7 —
> exactly the layout already drawn in `docs/XIAO-PINOUT.md`). For the bare XIAO
> module use (b); for shields/carriers use (a).

**Recommendation: `kiutils`** for the offline build step (a `scripts/` tool that
emits `board-geometry.json`), because it needs no KiCad install, pins cleanly in
`pyproject`/`requirements`, and reads both `.kicad_pcb` and `.kicad_mod`. Keep
`pcbnew` as a cross-check (it's already installed) and as the engine behind
`kicad-cli` for the 3D export. There is **no Dart/Flutter KiCad parser** — parse
offline in Python, ship JSON; never parse `.kicad_pcb` on-device.

### 1d. Exporting 3D (glTF/GLB) — the phase-2 model

KiCad 9+ ships `kicad-cli pcb export glb` (binary glTF). Confirmed available in
our KiCad 10 (`/usr/bin/kicad-cli`):
```
kicad-cli pcb export glb \
  --output board.glb \
  --include-tracks --include-pads --include-zones \
  --subst-models \
  "in.kicad_pcb"
```
Useful flags: `--board-only` (no parts), `--no-dnp`, `--no-unspecified`,
`--grid-origin`/`--drill-origin` (to control the model origin — pick the same
origin used for `board-geometry.json` so 2D and 3D overlays register).
glTF/GLB is the right interchange format: it is exactly what the Flutter 3D
packages load. Also supported: STEP, VRML/WRL, STL, BREP, PLY, U3D, PDF-3D.

Docs: https://docs.kicad.org/9.0/en/cli/cli.html (see `pcb export glb`/`gltf`).
KiBot wraps the same engine for batch/CI: https://kibot.readthedocs.io/en/latest/configuration/outputs/export_3d.html

**Boards where the full module PCB isn't open (e.g. bare XIAO C6):** the wiki
publishes a **GrabCAD STEP/3D model** (link below). Import that into KiCad or
convert STEP→glTF (FreeCAD, `assimp`, or `gltf-pipeline`) to get a `.glb`. For
phase 1 you don't need it at all — the footprint + pad table is enough for the 2D
dots.

## 2. Mapping geometry → logical pins (the join)

Two halves meet on the **pad label**:

**Geometry half (this doc):** from KiCad we get, per pad, `(pad_label, x_mm,
y_mm, layer, net_name)`. The `pad_label` is either the numbered pad mapped through
the fixed XIAO order (bare module) or directly the net name (shield header).
Normalise to the canonical XIAO pad names `D0..D10, 5V, GND, 3V3`.

**Logical half (already built):** `docs/XIAO-PINOUT.md` +
`scripts/gen-xiao-pinout.py` read each board's Zephyr connector node
`xiao_d { compatible = "seeed,xiao-gpio"; gpio-map = <0 0 &gpio0 1 0>, … >; }`
(in `seeed_xiao_connector.dtsi`) and produce `pad → GPIO number` per chip. Example
(C6): `D0→GPIO0, D1→GPIO1, D2→GPIO2, D3→GPIO21, D4→GPIO22, D5→GPIO23, D6→GPIO16,
D7→GPIO17, D8→GPIO19, D9→GPIO20, D10→GPIO18` — note it **differs per chip** (the
same `D0` is GPIO2 on C3, GPIO0 on C6), so the join must be keyed by `(board,
pad)`, never by GPIO number.

**The join, end to end:**
```
pad geometry           pad→GPIO (Zephyr)        live register
(KiCad)                (gen-xiao-pinout)        (our debugger)
─────────────          ─────────────────        ─────────────
D4 @ (x,y) ──────────► D4 = GPIO22 (on C6) ────► GPIO_OUT bit 22
   (clickable dot)        (board-specific)         (highlight colour)
```
Output of the build step is one record per pad:
`{ "pad": "D4", "x": …, "y": …, "layer": "top", "net": "D4_SDA", "gpio": 22 }`
— a clickable physical dot wired to a live GPIO register bit. The viewer polls the
debugger for the GPIO state and recolours the dot.

Power pads (`5V/GND/3V3`) have geometry but **no GPIO** — render them statically.

> The pad→GPIO machinery already exists and is tested (`gen-xiao-pinout.py`,
> `edt.pickle`/board-source backed, CI-checkable). The **new** work is purely the
> geometry extractor and the join on `pad` — keep the GPIO half as-is.

## 3. Rendering in Flutter

### 3a. Phase 1 — 2D PCB outline + pin dots (CustomPainter) ⭐ ship first

No package, no GPU, no WebView, no 3D toolchain. A `CustomPainter` that:
1. loads `board-geometry.json` (bundled asset),
2. draws the Edge.Cuts polygon as a filled `Path` (PCB silhouette),
3. draws each pad as a `Canvas.drawCircle`, coloured by live GPIO state,
4. draws component bodies as light rects (optional),
5. `GestureDetector` / hit-test (point-in-circle) → tap a pad → pin detail,
6. one `Matrix4`/`InteractiveViewer` for pan+zoom, and a top/bottom toggle
   (filter pads by `layer`).

This is the lowest-risk, highest-value view and covers the core requirement
(highlight per-pin state at the right physical spot) on every Android device with
zero native dependencies. KiCanvas (below) proves the model; we only need a tiny
subset in Dart.

### 3b. Phase 2 — glTF 3D model the user rotates

Cost: WebView dependency, localhost server, stale-Chrome blank-screen gotcha on old Android. **Recommendation:** start phase 2 with **model_viewer_plus** (or
`flutter_3d_controller` for the Dart camera API) to display `board.glb` and let the
user orbit — fastest path, accepting the WebView caveat. Keep the *interactive
pin overlay* in the **2D layer** (project the 3D camera or just keep phase-1 hit
testing for selection) rather than fighting the web component's picking. If the
3D overlay/picking becomes central, revisit **flutter_scene** once it stabilises
on the stable channel (it's the cleanest native path for our own hit-testing).

### 3c. Prior art to study

- **KiCanvas** — browser KiCad viewer, **vanilla TS + Canvas/WebGL**, parses
  `.kicad_pcb`/`.kicad_sch` (KiCad 6+), pan/zoom, select & inspect footprints,
  layer toggles. This is *exactly* the renderer we're cloning a subset of; read
  its parser + board renderer. https://github.com/theacodes/kicanvas ·
  https://kicanvas.org · author writeup https://blog.thea.codes/introducing-kicanvas/
- **KiCad → WebGL** survey: https://rbts.co/Blog/kicad-to-webgl-the-road-so-far/
- EasyEDA / JLCPCB web viewers (closed, but confirm the "outline + pads + 3D body"
  model is the standard one).
- Our own precedent for vendoring a small pure-Python parser instead of a heavy
  dependency: this repo (the pure-Python JTAG client). Same pattern fits a
  tiny `.kicad_pcb` reader if `kiutils` ever proves too heavy.

## 4. The "whole setup" diagram (later sub-goal — feasibility only)

Rendering **board + attached shields together** (CAN shield, RGB matrix, camera)
is feasible and falls out of the same data, but is explicitly **phase 3+**:

- Each board/shield already has (or can get) its own `board-geometry.json` and/or
  `.glb` by the §1 pipeline. The vendored shield PCBs (CAN board, Debug Mate) even
  carry the XIAO header **net names**, so the shield's header pad ↔ XIAO pad ↔ GPIO
  chain is fully recoverable from KiCad alone.
- **Stacking transform.** The XIAO module plugs into the shield's XIAO header at a
  known offset/rotation; a small per-combo transform (or aligning on the shared
  header pad coordinates) composes the two geometries. In 3D, place each `.glb`
  with a `Matrix4` (a board-stack manifest: which shield, what z-offset).
- **Electrical truth** of what a shield pin connects to (e.g. CAN board: D7=CS,
  D8=SCK…) is already captured for our bench in `docs/XIAO-PINOUT.md` §"Per-board
  connections" and `scripts/esp32-devices.json` — the diagram would *read* that,
  not re-derive it.
- Risk: each new shield needs its KiCad/3D asset + a placement transform; there's
  no auto-discovery of physical stacking. Fine as a curated, per-combo manifest;
  do **not** try to solve generally now.

## Phase plan (summary)

| Phase | Deliverable | Inputs | Flutter | Risk |
|---|---|---|---|---|
| **1** | 2D PCB outline + pin dots, live-coloured, tappable | `board-geometry.json` (kiutils build step) + `gen-xiao-pinout` GPIO map | `CustomPainter` + `InteractiveViewer` | **Low** — no native deps |
| **2** | Rotatable 3D board | `board.glb` (`kicad-cli pcb export glb`) | `model_viewer_plus` / `flutter_3d_controller`; later `flutter_scene` | Med — WebView/preview caveats |

**Do phase 1 first.** It satisfies the core requirement (live per-pin highlight at
the correct physical location) with the least machinery and produces the
`board-geometry.json` that every later phase reuses.

## Risks & unknowns

- **Bare XIAO module pad labels:** the standalone `.kicad_mod` has only numbered
  pads (1–14) and no nets — label mapping must come from the fixed XIAO order
  (already in `docs/XIAO-PINOUT.md`) or from Seeed's full C6 KiCad project. Verified
  by extracting `XIAO-ESP32-C6-DIP.kicad_mod` locally: pads `"1".."14"`, silk
  outline only, **no** `D0`/`3V3` text.
- **TinyC6 has no published full `.kicad_pcb`** (footprint + STEP/3D model only) —
  phase-2 3D must come from its STEP/GrabCAD model, converted to glTF.
- **`board-geometry.json` is a derived artifact** (per project rules): regenerate
  from KiCad on demand; no migration, no schema fallback — the build step *is* the
  migration. Don't hand-edit it.
- **model_viewer_plus / Android:** depends on a current system WebView (old Chrome
  → blank screen) and a localhost HTTP server; picking inside the web component is
  a black box. Keep interactive selection in the 2D layer.
- **flutter_scene / Flutter GPU** is preview-only (main channel, Impeller) — don't
  bet phase 2 on it yet, but track it; it's the cleanest native picking path.
- **Coordinate alignment:** ensure the 2D extractor and the glTF export use the
  **same origin** (e.g. both `--drill-origin`/grid origin), or the 2D overlay won't
  register on the 3D model. KiCad Y is down; flip if your render space is Y-up.
- **Arc tessellation:** Edge.Cuts uses `gr_arc` (start/mid/end) — flatten to short
  chords for the 2D `Path`; `pcbnew` does this for you if you go that route.
